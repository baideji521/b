## 瓶颈定位：耗时全在 generate

所有 8 个组合里 `generate` 占视觉总耗时 85%~93%，`processor` ≤0.3s，`text_decode` ≈0。
帧解码（3.7~7.3s）只随帧数变化，是第二项但量级小。

结论：**降 fps / 降帧数 / 降分辨率 / 降 max_new_tokens 都只能小幅改善**，因为它们
不改变"每个窗口要串行解码几百个 token"这件事。真正的杠杆是**窗口批处理**。

## 逐级扫描结果（阶梯式，每次只动一条轴）

1. fps（1.5 → 1.0 → 0.75 → 0.5）：配置 A→C 视觉 43.4s → 41.1s，只省 5%。
   fps 再降到 0.5（配置 D）事件会被合并成一条，覆盖率下降，不采纳。
2. 帧数（16 → 12 → 8 → 6）：帧数减半只省掉解码时间（7.2s → 3.7s），generate 几乎不变。
   8 帧是"每个 15s 窗口仍能看清动作变化"的下限，6 帧开始丢中间动作。
3. 分辨率（每帧像素预算，1 token = 32×32 px）：
   - 112 tokens/帧（288×384）：峰值 9.4~9.6GB，视觉 41~42s
   - 300 tokens/帧（480×640）：峰值 11.8GB，视觉 90.9s
   - 432 tokens/帧（576×768）：峰值 reserved 14.4GB → 溢出到 Windows 共享内存，视觉 330.6s
   - 675 tokens/帧（704×960）：reserved 20.3GB，视觉 653.9s
   - 854 tokens/帧（800×1088）：reserved 26.9GB，视觉 1158.6s（RTF 23.6，完全不可用）
   原始扫描数据见 `benchmark/resolution_sweep.json`。
   **注意**：那份文件里的 "Recommended 800x1088" 结论已作废——它的 quality_score 把
   "与参考分辨率的描述一致度"算进分数，而参考分辨率就是 800×1088 自己（自参考偏差恒为 1.0）。
   按本轮 ground_truth 重新评分后，288×384 在人数、覆盖率、幻觉率上与高分辨率无差别，
   而 OCR 在任何分辨率下都读错（见 quality_report.md），所以不上调分辨率。
4. 窗口 / overlap（15.0s / 3.0s）：窗口越长每窗口 token 越多但窗口数越少，
   15s/3s 是"4 个窗口覆盖 49s 且事件不被切碎"的组合，没有找到更优解。
5. max_new_tokens（512 → 384 → 256 → 192 → 128）：4B 在配置 C 实际只生成 462 token 均值，
   192 已经够用（输出被提示词压到最多 5 条事件）；128 会在窗口事件较多时截断 JSON。
6. **batch_size（1 → 2 → 4）：43.4s / 41.9s / 27.7s，峰值显存 9.7GB 仍在 12GB 内。**
   这是整轮扫描里唯一的大幅提升（-34%），因为它把单步解码的固定开销摊到 4 个窗口上。
   最终配置采用 batch_size=4。

## 显存墙（RTX 3060 12GB 实测）

torch reserved 超过约 12GB 后 Windows 会把超出部分放到共享内存（system RAM），
不报 OOM，但速度掉到 1/3 左右（576×768：42s → 115s 级别，见上面分辨率扫描）。
因此 OOM 阶梯的第一优先级是 batch，其次帧数，再分辨率，最后 max_new_tokens。
